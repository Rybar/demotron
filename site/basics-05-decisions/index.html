1 Comparisons

In Basics 4, btn(1) asked a question and if acted on the answer. This lesson asks questions of our own: is the circle past the middle, has it reached the edge? We'll use the answers to keep a circle on screen, change its colour and bounce a ball off the walls, and finish with a ball and a paddle ready to become a one-player Pong.

A question like "is x bigger than 240?" is a comparison. It takes two values and answers true or false. There are six:

  • x > 240 and x < 240: bigger than, less than
  • x >= 240 and x <= 240: bigger than or equal, less than or equal
  • x == 240: exactly 240
  • x != 240: anything other than 240 (Lua's own spelling is ~=, and Picotron accepts both)

Note the double equals. One = puts a value into a variable; two, ==, ask whether two values are the same. Mixing them up is one of the most common slips in programming.

Move the circle across the line and watch the answers change. They go through tostr() first because .. can only join text and numbers, and tostr turns true or false into text.

Try this

  • Change the start to x = 100, hold right and watch x == 240 as the circle crosses the line. Then set speed = 3 and try again. Predict before each run whether you'll ever see true, then work out why by thinking about which numbers x actually lands on.
  • Change one of the == into a single = and run it. Picotron refuses to start. Read the message: which line does it point at, and what was it expecting to find? Why might it be a good thing that Lua refuses instead of guessing what you meant?
  • Add a line that prints tostr(btn(1) == true) and hold right. Before you run it, remember what btn answers with (slide 2 of Basics 4). Were you right? What would you write instead?

2 Screen edges

This is Basics 4's four-way movement with one problem fixed: hold an arrow and the circle stops at the edge instead of sliding off into nowhere.

The fix is four decisions made after the movement, on lines 11 to 14. We move first, then check: if x has gone below 8, put it back to 8. The 8 is the circle's radius, so at x = 8 its left side just touches the edge of the screen. The last column of pixels is 479, so on the right the centre can go up to 479 - 8 = 471. The bottom is the same sum with the last row: 269 - 8 = 261.

The other way to do it is to only move when there's room. That works here, but every new way of moving (a dash, a knockback, a teleport) would need a check of its own. Correcting afterwards doesn't care how the circle got too far: whatever happened this frame, these four lines tidy up before anything is drawn. "Move, then correct" turns up in almost every game, and we'll lean on it again on slide 6.

Try this

  • Instead of stopping at the edges, make the circle wrap: off the right side, back on at the left, and the same for top and bottom. Play with both versions. Which feels better for a spaceship, and which for a person walking around a room?
  • Make the circle twice as big (radius 16). What else has to change so it still stops snugly at every edge? Then rewrite it so one variable, r, sets the size, and the edges follow along by themselves.
  • Turn the circle a different colour while it's pressed against a wall, and back to blue when it isn't. Which lines of code only run on the frames when it's touching?

3 Clamping

Those four ifs work, but each one is a chance to type the wrong number or point a < the wrong way. Keeping a number between two limits is common enough that Picotron has a function for it: mid(a, b, c) gives back whichever of its three numbers is in the middle.

So mid(8, x, 471) is 8 when x is less than 8, 471 when it's more than 471, and x itself anywhere in between. This is called clamping. One line for x and one for y now do what four ifs did before.

The circle behaves exactly as it did on the last slide. I use mid, because two lines leave fewer numbers to get wrong than four, and you'll see it a lot in other people's Picotron code.

Try this

  • Does the order of the three numbers matter? Predict what x = mid(471, x, 8) does, then try it.
  • In Basics 3 you met max, which gives the bigger of two numbers; min gives the smaller. Rewrite the clamp using max and min instead of mid. Which of the two stops the circle at the left edge?
  • A Picotron quirk: predict what max(1, 5, 9) gives, then print it and see. Why could this cause a bug that's hard to spot?

4 else and elseif

So far every if has meant "do this, or do nothing". Often we want "do this, otherwise do that", which is what else is for.

For more than two choices, elseif adds another question to the chain. Lua asks them from the top down: the first one that answers true has its lines run, and the rest of the chain is skipped. If none is true, the else lines run. Exactly one branch runs, every time.

Here the circle's colour depends on which third of the screen it's in. Reading from the top: if x is less than 160, red; otherwise, if it's less than 320, green; otherwise, blue. The second question doesn't need to say "and at least 160", because if x were smaller than that, the first branch would already have won.

Try this

  • Swap the first two questions, so x < 320 is asked before x < 160. Before you run it, predict which colour you'll never see again, and explain why.
  • elseif is one word. Write else if as two words instead and run it. What does Picotron complain about? Can you make the two-word version work, and what does that tell you about what else if really means?
  • In Basics 3 you met \, which divides and rounds down. Replace the whole chain with a single line that sets col to 8, 9 or 10 depending on the third. Which version would you rather change if you wanted six zones?

5 and, or, not

Sometimes one question isn't enough. "Is the circle inside the box?" is really four: is it right of the box's left side, and left of its right side, and below its top, and above its bottom?

and joins two questions and is only true when both are. Chain several and every one has to be true, so the box lights up only while all four agree. The chain is split over lines 16 and 17; Lua keeps reading until it finds then.

or is true when either side is (or both), and not flips an answer: not true is false. Basics 4 already used or once: btn(b) or 0 works because or gives back its first value when that counts as "yes", and its second value otherwise.

Try this

  • Make the box light up only while the circle is inside it and O is held. Then give it a third colour for "O is held, but you're outside".
  • Right now it's the circle's centre that has to be inside. Change the questions so the box lights up as soon as any part of the circle touches it. (Think about the radius.)
  • not is greedy: it grabs only the thing right after it. Try if not x > 240 then and read the error. What did not actually get applied to, and how do brackets fix it?

6 Bouncing

Until now the circle only moved when we pushed it. This ball moves by itself, and decisions change how it moves.

dx and dy are its velocity: how far it travels across and down each frame, added to x and y every frame. A positive dx moves right and a negative one moves left, so a bounce off a side wall needs no new direction worked out. dx = -dx flips the sign: 3 becomes -3, and -3 becomes 3.

After a bounce, mid clamps the ball back onto the screen: move, then correct, as on slide 2. Drag the sliders: each one sets a velocity, and the next wall flips it. Try a negative value, or 0.

Try this

  • The mid lines look like they do nothing: delete them and the ball still bounces. Now start the ball at x = 475, just past the right edge. Predict what happens, then run it. What were the mid lines protecting you from?
  • Add gravity: dy += 0.2 every frame. Does the ball keep bouncing to the same height forever? Make it lose a little height on each bounce off the floor, like a real ball.
  • Make the ball change to a random colour each time it hits a wall, and only then. Which lines run exactly once per bounce?

7 Putting it together

In this lesson we added:

  • comparisons, which answer true or false
  • "move, then correct" for keeping things on screen
  • mid for clamping a number between two limits
  • else and elseif for choosing one branch of several
  • and, or and not for combining questions
  • velocity, and bouncing by flipping its sign

Every one of those is the same idea: ask a question, then act on the answer. The starter here has a paddle that moves with left and right and stays on screen, and a ball that bounces off all four walls. Nothing connects them yet. Copy it into a new cart and start with the first idea below. Next, Basics 6 goes from one ball to many things at once, with lists.

Try this

  • Pong for one: take away the bottom wall so the ball can fall off the screen, and make it bounce off the paddle instead. When the ball is lost, put it back near the top. (The paddle question is an and chain, like the box on slide 5. If the ball wobbles inside the paddle, remember the stuck ball on slide 6.)
  • Count how many times in a row you return the ball, print it, and start again from 0 when you miss. Then keep a best score that only changes when you beat it.
  • Make the paddle aim: hits near its ends send the ball off at a steep angle, and hits near the middle send it almost straight up. x - px tells you how far from the middle the ball landed.
