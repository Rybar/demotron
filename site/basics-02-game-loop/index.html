The Game Loop

Your _update is about to run 216,000 times an hour.

notes.txt

1 Sixty Pictures

The first program we ran in Getting Started looked like a still picture:

1function _draw()
2  cls(1)
3  circfill(240, 120, 30, 12)
4  print("hello, picotron!", 200, 170, 7)
5end

We never called _draw ourselves. Picotron calls it, which means it runs the lines inside, 60 times a second for as long as the program runs. Each call paints one picture over the whole screen, called a frame. That circle got painted in exactly the same spot every frame, so nothing seemed to happen.

If we paint each frame a little different from the one before, things move. Pip walks because every frame has Pip a pixel and a half further along, and at 60 a second our eyes see a chick walking and miss the jumps.

The first thing I ever made was a rocket countdown on a Tandy Color Computer 2, the rocket drawn in text characters. Same trick.

Drag fps (frames per second) down to 4 or so and walk Pip.

60 a second leaves 16.67 milliseconds for each frame, and all our code has to fit in it.

2 Update, Then Draw

_draw paints the picture, and to change it between frames we give Picotron a second function, _update:

1x = 60
2
3function _update()
4  x += 8
5end
6
7function _draw()
8  cls(12)
9  circfill(x, 200, 10, 10)
10end

x is a variable, which is a name that holds a number. x += 8 adds 8 to whatever is in it, and Basics 3 is all about both.

Every frame starts with a call to the update, and the draw comes straight after. The update moves x to 68 and the draw paints the circle there. Then x goes to 76 and the circle follows it. Update, draw, update, draw, forever. This is the game loop, and every Picotron game runs on one.

The dotted white Pip is where x already says Pip is, before the draw has painted it there. Drag fps up to 60 and Pip's 8 pixels an update come to 480 a second, the width of the screen, so it crosses in one second flat.

Note: If you're coming from PICO-8, there's no _update60 in Picotron. Plain _update already runs 60 times a second, and a function by that name never gets called at all. The manual still mentions it in a couple of places, where it means plain update.

3 Seconds with t()

1print(t(), 8, 8, 7)

t() gives us how many seconds the program has been running, and time() is the same function with a longer name.

It doesn't look at a real clock. It counts updates instead, adding 1/60 of a second for each one, so 60 updates is exactly one second, and when a game gets so slow that Picotron can't manage 60 updates a second, the count slows down with it.

Multiply it and we get a speed in pixels a second, with no variable at all:

1circfill(40 + t() * 30, 100, 10, 10)

We get 30 pixels a second, starting at 40. The slide rounds the seconds to two places. Print the real thing and you get 2.0333333333333, because 1/60 never comes out even as a decimal.

4 Wipe with cls

1function _draw()
2  cls(12)
3  circfill(x, 200, 10, 10)
4end

Picotron never clears the screen for us. Whatever the last frame painted is still there when the draw starts, so we begin most draws with cls(12), which fills the whole screen with colour 12, the light blue of the sky. Plain cls() fills it with colour 0, black.

Turn clear off and walk about. Anything painted in the same spot every frame, like the sun, covers its own mess. Anything that moves leaves a trail.

5 Back to Front

A draw paints in the order its lines run, and each thing lands on top of whatever's already there:

1cls(12)                      -- the sky
2circfill(396, 168, 30, 10)   -- the sun
3circfill(400, 350, 190, 27)  -- a hill, over the sun
4circfill(x, 200, 10, 10)     -- Pip
5circfill(300, 190, 24, 3)    -- the bush, over Pip

Here we paint Pip before the bush, so when Pip walks behind it the bush wins. If we swap the last two lines, Pip walks in front, which is what pip_last does on the slide.

Painters do the sky first and put the hills over it, so this is called the painter's algorithm. Set steps to 3 and the draw stops after the hills. No bush, nobody home.

6 Set Up with _init

1function _init()
2  x = 50
3  berries_left = 6
4end

_init runs once, before the first update. In it we set where Pip stands and how many berries are left.

Lines at the top of the file, outside any function, run once too, but they run earlier, while Picotron is still reading the file. A function written further down doesn't exist yet when they run. _init waits until the whole file has been read, so it can use anything in it.

And it's a function, so we can call it ourselves to start over:

1if (berries_left == 0) _init()

if runs the rest of its line only when the test in its brackets is true, here when every berry has been eaten. == asks whether two things are equal. One = would put 0 in berries_left instead.

Calling _init() doesn't restart the program. It reruns our set-up lines, and everything else carries on, t() included.

7 Move in _update

You could put everything in _draw, and in most small programs you'd never notice. You notice when drawing gets slow.

If our code takes longer than 1/60 of a second, the frame runs late. Picotron drops to 30 draws a second with two updates before each one, or 20 with three. Anything moved in _update keeps its speed, and anything moved in _draw only moves when a draw runs:

1function _update()
2  pip_x += 1.5    -- 60 times a second
3end
4
5function _draw()
6  frog_x += 1.5   -- only when a draw runs
7  cls(12)
8end

Set busy to 1 and then 2 and watch the readouts.

Anything that changes the game goes in the update, and the draw just paints. Keep to that even in tiny programs, because you won't know a draw is too slow until it is.

Note: Where's delta time? There isn't any. Every update is 1/60 of a second of game time, so a game that bogs down below 20 draws a second goes into slow motion instead of jumping ahead.

8 Try It

This lesson's try-it demo is a small sunset program.

  • _init puts the cloud just off the left edge at x = -80. The update calls it again once the cloud's past 500, so the cloud keeps coming round (slide 6).
  • The update moves the cloud a pixel at a time, which makes 60 pixels a second (slides 2 and 7).
  • cls(29) paints the lilac sky over the last frame before anything else goes on (slide 4).
  • The draw paints back to front, so the hills cover the sun as it goes down (slide 5).
  • t() sinks the sun 2 pixels a second, and the last line prints it (slide 3).

Calling _init() brings the cloud back but never the sun, because the seconds don't start over. The sun is behind the hills about 31 seconds in, and after that the sunset is a cloud going round forever. Fixing that needs a number we keep ourselves, which is Basics 3.

Start up Picotron, copy the code below and paste it into the code editor's main.lua, then press Ctrl + R.

try.lua
1-- sunset: the sun sinks behind the hills
2-- while a cloud drifts by, again and again
3
4function _init()
5  x = -80  -- where the cloud is
6end
7
8function _update()
9  x += 1   -- one pixel every update
10  -- gone off the right? start over
11  if (x > 500) _init()
12end
13
14function _draw()
15  cls(29)  -- paint the sky over everything
16
17  -- the sun sinks 2 pixels a second
18  circfill(360, 150 + t() * 2, 36, 9)
19  circfill(360, 150 + t() * 2, 30, 10)
20
21  -- the hills, painted over the sun
22  circfill(110, 330, 190, 13)
23  circfill(400, 350, 180, 3)
24
25  -- the cloud, painted over the sky
26  circfill(x, 60, 16, 7)
27  circfill(x + 22, 50, 22, 7)
28  circfill(x + 46, 60, 16, 7)
29
30  -- how long it's been running
31  print("seconds:", 8, 8, 7)
32  print(t(), 48, 8, 7)
33end

Try This

  • Bring the cloud down to the sun's height and make it drift behind the sun.
  • Add a second cloud that's smaller and lower than the first and goes faster.
  • Print how many clouds have gone by under the seconds, and keep the count from going back to 0 every time _init runs.
  • Turn the sky dark blue once the sun has gone behind the hills.
