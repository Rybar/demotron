The game loop

The three functions Picotron calls to run a game, what belongs in each, and the order they paint in.

2frames = 0

1 Frames

A game has to keep running while the player does nothing. Most programs run from top to bottom and then finish, but a game has to keep watching the buttons and keep the picture moving for as long as someone is playing. In this lesson we build the frame every Picotron game hangs on, and finish with a tiny screensaver.

Picotron does the looping for us. If a program has functions called _update and _draw, Picotron calls them over and over: _update, then _draw, then _update again, about 60 times a second, until the program stops. Each _update and _draw pair makes one frame, like one page of a flipbook. Flip the pages fast enough and things seem to move.

The demo counts frames. _update adds 1 to frames each time it runs, and _draw prints the number. Nothing in the code says "repeat": Picotron does the repeating.

Under the count is t(), short for time(): the number of seconds since the program started. Watch how the two numbers grow together.

Try this

  • Predict what the frame counter will say when t() reaches 10. Then paste the code into a new cart, run it with Ctrl-R and watch to check. (A few frames out counts as right.)
  • Add a second counter, draws, that goes up by 1 in _draw, and print it too. Will it keep pace with frames? Now give _draw far too much work: just after cls(1), add for i = 1, 200 do circfill(240, 135, 100, 2) end, which paints the same big circle 200 times. Watch both counters and t(). Which one falls behind, and why might Picotron have chosen that one?
  • Move the three print lines out of _draw and into _update, just after frames += 1, and leave cls(1) where it is. Predict what you'll see before you run it, then explain what happened.

2 Clearing the screen

Here's a ball bouncing around the screen. Every frame, _update moves it a few pixels and _draw paints it at its new spot. (The two if lines turn it round at the edges; Basics 5 covers if properly.)

The first thing _draw does is cls(1), which clears the whole screen to colour 1, dark blue. Picotron never wipes the screen for us. Each frame starts with whatever the last one left behind, so a game clears the screen and paints the whole picture again, from scratch, every frame.

Drag clear to 0 to skip the cls. Every ball that was ever painted stays where it was, and we get a trail. Drag it back to 1 and the trail vanishes in a single frame, because one cls wipes the lot.

So we never "move" a ball on screen. We change its x and y, then paint a fresh picture with the ball in its new place. Rubbing out only the old ball sounds cheaper, but then we'd also have to repaint whatever was behind it. Repainting everything is simpler, and it never leaves a mess behind.

Try this

  • Move cls(1) to the very end of _draw, after the circle. Predict what you'll see, then try it.
  • With clear set to 0 the trail lasts forever. Make it wear away instead: at the start of _draw, paint a background-coloured blob somewhere random, circfill(rnd(480), rnd(270), 40, 1). The old trail gets nibbled away a bit at a time. Why does the newest part of the trail always look solid?
  • Give the ball a colour variable and change it every time the ball bounces (the bounce lines are a good place for that). Then turn clear off: the trail becomes a record of every bounce.

3 Timing

Picotron makes a promise about _update: it runs 60 times a second, always. _draw usually does too, but when painting a frame takes too long, Picotron skips some _draws and drops to 30 frames a second (or lower) so that _update keeps its pace. The game looks a little choppier, but unless it's hopelessly overloaded, it doesn't slow down.

That makes _update the place for anything that needs a steady beat: movement, timers, the rules of the game. I keep _draw for painting and nothing else, so a slow frame can only cost smoothness, never game speed.

t() runs on the same beat. The Picotron manual explains that it isn't read from a real clock; it's worked out by counting _updates. Here the circle's position comes straight from it: t() * pps is how far it would have travelled by now, and % 480 takes the remainder after dividing by 480, which wraps that distance back onto the screen. (Basics 3 covers % properly.)

Drag pps (pixels per second) to change the speed. At 60, the circle takes 8 seconds to cross the screen, because 480 ÷ 60 = 8.

Try this

  • Drag the slider slowly and watch closely: the circle doesn't just speed up, it jumps to a new place. Why? Rewrite _update so that changing pps only changes the speed, never the place. (A clue: pps / 60 is how far to move in one update.) To test it in Picotron, where there's no slider, add if t() > 3 then pps = 180 end and watch what happens at 3 seconds.
  • Make a clock: print flr(t()) in big numbers in the middle of the screen (flr rounds down, so you get whole seconds). Then make the circle pulse by giving it a radius of 12 + sin(t()) * 6. How long does one pulse take? A clue: Picotron's sin measures angles in whole turns, not degrees.

4 One-time setup

Some things should happen only once: choosing where the player starts, setting the score to 0, building the first level. That's the job of _init. Picotron calls it once, after it has read the program and just before the first _update.

This _init gives the circle a random colour and a random spot. rnd(400) is a random number between 0 and 400, and rnd({...}) picks one item from a list. The two counters show how often each function has run: _update races upward, but _init stays at 1.

When a program restarts, everything begins again from the top, _init included. In Picotron that happens every time you press Ctrl-R; on this page it happens whenever you come back to a slide. Visit another slide and come back: the circle gets a new colour and a new spot, but the counter still says 1, because the old run, counters and all, is gone.

Try this

  • Move the three setup lines (col, x and y) out of _init and up to the top of the file, under updates = 0. Run it a few times. Does anything change? Keep the next challenge in mind, and think about when it would matter which place you chose.
  • Restart without restarting: add if btnp(5) then _init() end to _update, so pressing X makes your own code call _init. (btnp(5) is true at the moment X is pressed; Basics 4 covers it properly.) Predict what both counters will say after you've pressed X twice, then check.

5 Drawing order

The screen isn't a list of things like "a sun, a hill, a house". It's a canvas of 480 × 270 coloured pixels, and every drawing command paints over whatever is already there. Once the sun is painted, Picotron doesn't remember it was a sun. It's just yellow pixels.

So the order of the drawing commands is the order of the layers: the things at the back first and the things at the front last, the way a painter works. Drag step from 1 to 3: the sun goes on first, then the hill covers the bottom of it, then the house sits on top of the hill.

rectfill(x0, y0, x1, y1, col) fills a rectangle between two corners. The house is four of them, each one painted over the last.

Try this

  • Move the window's line so it comes before the walls. Predict what will happen to the window, then try it and explain why.
  • Make the sun set: give it a y that grows with t(), so it sinks a few pixels each second. Does it slide behind the hill or in front of it? What would you change to get the other one? For a finishing touch, make the sky darken once the sun is out of sight.

6 Putting it together

In this lesson we learned:

  • _update, called 60 times a second, for anything that changes
  • _draw, which clears and repaints the whole picture every frame
  • _init, called once, just before the first _update
  • t(), the seconds since the program started, counted in updates
  • drawing back to front, because every command paints over the last

The starter is an empty frame: a circle set up in _init, painted in _draw, and an _update with nothing in it yet. Copy it into a new cart in Picotron; the ideas below turn it into a tiny screensaver. Next, Basics 3 looks properly at the numbers we've been leaning on here: variables, %, rnd and loops.

Try this

  • Make the circle drift around the screen on its own, steered only by t(). (A clue: cos and sin of the same angle give you a point on a circle.) Can you make its path an oval instead?
  • Change the circle's colour once every second. flr(t()) only changes once a second, so it's a good start. How could you turn it into a colour number that stays between 1 and 15? (Slide 3 used something that wraps numbers.)
  • Show how long the screensaver has been running, in whole seconds, in a corner. Then add slide 4's trick, pressing X to call _init() again, and make the count go back to 0 when you do. t() itself never goes back, so what could _init remember to make that work?
