1 Arithmetic

Most of a game is numbers: where things are, how fast they're moving, how many lives are left. Before we can move anything around we need Picotron to do sums, and by the end of this lesson we'll be keeping score, timing things, repeating work and rolling dice. It's a lot of small tools, so each slide adds one.

Each line of the demo is two print calls. The first prints text in quotes, exactly as written. The second has a sum outside the quotes, so Picotron works it out first. .. joins two things into one piece of text, which is how "= "..(2 + 3) becomes = 5. The brackets keep the sum together.

The order is the one from school: ^ (a power, so 2 ^ 8 is eight 2s multiplied together) first, then * and /, then + and -. That's why 10 - 4 * 2 is 2 and not 12. Brackets go first when we want something else.

The last answer prints as 256.0, with a .0 on the end. That's not a typo; it's the subject of slide 3.

Try this

  • Without running anything, work out 2 + 3 * 4 ^ 2. Then add a pair of lines to the demo to check your answer. Now add brackets, without changing any of the numbers, so the answer becomes 400.
  • Predict -2 ^ 2, then add it and check. If the answer surprises you, work out which happens first, the minus sign or the power, and how brackets would change it.
  • Predict what "2" .. "3" and "2" + "3" give, quotes and all, then add them to the demo and check. Is either answer a real number, or just text that looks like one? (Slide 3 shows a way to find out.)

2 Variables

A game has to remember things from one frame to the next: the score, the lives, how long until the next enemy turns up. We keep each of those in a variable, a name with a value attached.

score = 0 makes a variable called score holding 0. From then on, wherever the code says score, Picotron uses whatever value it holds at that moment. score += points is shorthand for score = score + points: work out the new total and store it back under the same name.

We want points once a second, not once a frame, so a second variable, timer, counts frames. _update runs 60 times a second, so when timer reaches 60 a second has gone by: we add the points and set timer back to 0. (The if line means "only when this is true"; Basics 5 covers it properly.)

Drag the points slider. The score carries on from where it was, because the variable keeps its value; only the amount added each second changes.

Try this

  • Move the line score = 0 to the very top of _update, just above timer += 1. Predict what the score will show, then run it. What does that tell you about where a variable that has to remember belongs?
  • Change score to scroe in the print line only, and run it. Read Picotron's error: what does it say is nil (Lua's word for "nothing"), and why can't it guess which variable you meant?
  • Make every award worth twice the one before: after score += points, add points *= 2 (*= works like +=, but multiplies). Predict how many seconds it takes for the score to pass a million. Then leave it running for a little over a minute, and keep watching.

3 Integers and floats

Back to that .0. Picotron's Lua has two kinds of number. Integers are whole numbers, like 3, 0 or -12. Floats can have a fraction, like 3.5 or 0.25. math.type tells us which kind a number is, and the right-hand column of the demo shows it for each answer.

/ always gives a float, even when the answer is whole, so 10 / 2 is 5.0. ^ does the same, which is where slide 1's 256.0 came from. Most of the time it doesn't matter: the two kinds mix freely, and 5.0 is still five.

It matters when we need a whole number, such as a whole second or a square on a grid. There are two tools for that. \ divides and rounds down, so 7 \ 2 is 3. flr ("floor") rounds any number down, so flr(3.7) is 3. I reach for \ when I'm dividing anyway, and flr for everything else.

One oddity in the demo: inside quotes a backslash has a special job, so printing one takes two ("7 \\ 2 = "). Outside the quotes, 7 \ 2 is the real sum.

Try this

  • What is -7 \ 2? Predict, then add a line to check. Why does "rounds down" give that answer? (Picture the numbers on a line.)
  • Add a line for 0.1 + 0.2 - 0.3. It ought to be 0. Predict whether it will be, then check. A clue: just as 1/3 can't be written exactly as a decimal (Picotron shows 0.33333333333333), most fractions can't be stored exactly in a float.
  • Your calculator refuses to divide by zero. Predict what 7 / 0 and 7 \ 0 do in Picotron, then try them. Does the program stop? Are the two answers the same kind of number?

4 Remainders

% gives the remainder, what's left after dividing: 7 % 3 is 1, because 3 goes into 7 twice with 1 left over. 480 % 480 is 0 and 481 % 480 is 1.

That makes it the tool for anything that goes round and round. The obvious way to wrap the circle back to the left edge is to check x and reset it, and that works, but it's two lines and an if for every edge. x = (x + speed) % 480 does it in one: x grows each frame, and the remainder keeps it between 0 and just under 480. The x = readout shows the moment it wraps.

The blinking text uses the same trick on time. t() is the seconds since the program started, so t() % 1 is just the part after the point, running from 0 to nearly 1 every second. The text shows while that's under 0.5, which is half of each second.

Drag speed to 2.5 and watch the readout: x becomes a float, because adding a float to anything gives a float.

Try this

  • In your own copy, set speed = -3. Before you run it, predict: does the circle stop at the left edge, vanish for good, or come back on the right? Work out what -3 % 480 has to be for your answer, then check.
  • Slide 2's timer counted to 60 and was then reset by hand. Rewrite it so timer just keeps counting forever and the points still arrive once a second, using % instead of the reset.
  • Make the circle change colour four times a second, cycling through colours 8 to 15 and then back to 8. You'll want t(), % and flr: work out what each one does for you before you start typing.

5 Loops

Five circles could be five circfill lines. Fifteen circles would be fifteen nearly identical lines, and changing their size would mean editing every one. A for loop writes the line once and repeats it.

for i = 1, n do makes a variable i starting at 1, runs everything down to end, adds 1 to i, and goes round again until i has been every number up to n. Each time round, the circle is drawn at i * 30 pixels across, so they land at 30, 60, 90 and so on. Its colour is i as well, and the number under each circle is the i it was drawn with.

Drag n: one loop, any number of circles, and the code stays the same length. At 0 the loop doesn't run at all.

Try this

  • Make a grid of circles: put a second for (counting with j) inside the first, and use j for the y position. Then make each circle's colour depend on both its row and its column. Predict the pattern i + j will make before you run it.
  • Make the radius 20 so the circles overlap. Which one ends up on top, and why? Now predict what changes if the loop counts backwards with for i = n, 1, -1 do (the third number is the step).
  • Add up every number from 1 to 100: start a variable at 0, add i to it inside a loop, and print the total. A famous mathematician is said to have found the answer in his head as a schoolboy. Once you have it, can you spot his shortcut?

6 Random numbers

Games need things the player can't predict: where the next enemy appears, which way a spark flies. rnd(480) gives a random number from 0 up to (but never quite) 480, different every time we ask.

rnd returns floats like 217.38. That's fine for a position, but colours are whole numbers, so flr(rnd(16)) rounds down to one of 0 to 15.

Each frame, a loop like slide 5's drops per_frame dots at random places in random colours. _draw never calls cls, so every dot stays where it landed and the screen fills up. (The cls(0) in _init clears it once, at the start.) Drag per_frame to change how quickly. Every run of the demo lands differently.

Try this

  • Make the confetti land only in the middle third of the screen (which x values is that?), and only in the warm colours 8, 9 and 10. There are two ways to get those colours: one uses flr and +, and the other hands rnd a list in curly brackets, rnd({...}).
  • Put srand(42) inside _init, then run the cart a few times. What's different now? Why might a game want its "random" to come out the same every time?
  • Is flr(rnd(3)) fair? Use a loop to roll it 600 times, count how many 0s, 1s and 2s come up, and print the three counts. Roughly what should each one be, and does a 3 ever appear?

7 Putting it together

In this lesson we learned:

  • arithmetic, and .. for joining numbers onto text
  • variables that keep their values between frames
  • integers and floats, and \ and flr for whole numbers
  • % for anything that wraps or repeats
  • for loops
  • rnd for random numbers

That's enough to count, time and shuffle things, which covers a surprising amount of a game. The starter here has a frames counter and three empty slots. Copy it into a new cart; each idea below needs at least two of the tools above. Next, Basics 4 puts these numbers to work moving a player around with the arrow keys.

Try this

  • A countdown: show the seconds counting down from 10, as whole numbers, and stop at 0 instead of going negative. You'll meet max here: it takes exactly two numbers and gives back the bigger one.
  • A tiny slot machine: show a random number from 1 to 6 in each slot, changing every frame, until frames reaches 120. Then they freeze on their last numbers. (Each slot needs a variable of its own, so it remembers its number once it stops changing.)
  • Turn frames into a clock that reads minutes and seconds, like 1:05. You'll need \ and %, plus a little trick for the 0 in 1:05.
