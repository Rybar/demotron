1 Fields

At the end of Basics 6 the starfield kept each star's numbers in two lists: star 7 lived at xs[7], ys[7], and every add to one list needed a matching add to the other. Each extra number per star would mean another list to keep in step. This lesson keeps all of one thing's numbers together in one table, and ends with lists of objects that move and draw themselves, and come and go.

Here's the bouncing ball from Basics 5. It needs five numbers: where it is (x, y), how fast it's moving (dx, dy) and its colour. Line 2 puts all five in one table:

ball = {x = 240, y = 135, dx = 3, dy = 2, col = 10}

It's the same curly brackets as a list, but every value has a name. These named slots are fields, and a table of fields that stands for one thing in the game is an object. (Lua calls both lists and objects tables; a list is a table whose slots are numbered 1, 2, 3 instead of named.)

ball.x reads as "the ball's x", and works like any other variable, so ball.x += ball.dx moves the ball along. The bounce on lines 7 to 14 is Basics 5's, word for word apart from the ball. in front: flip the speed, then pull the ball back with mid. The printout in the corner shows the fields changing.

Try this

  • Under line 2, add other = ball and then other.col = 8. Before you run it, predict: what colour is the bouncing ball now? And is there one ball in your program or two? Check, then keep that answer in mind for slide 2.
  • Give the ball a radius: add r = 8 to the table and use ball.r in the circfill. Then make the walls use it too, so a ball with r = 30 still bounces with its edge touching the side of the screen. (What are 471 and 261 made of?)
  • Misspell a field: change ball.col in the circfill to ball.colour. Predict whether Picotron will stop with an error, then run it. What does Lua hand back for a field that was never set? Basics 6's scores[4] is a clue.

2 Lists of objects

Games want dozens of balls, so we put the objects in a list. balls is an ordinary list, like Basics 6's, except that every item is a whole ball table: balls[3] is the third ball, and balls[3].x is that ball's x.

Lines 8 to 12 build a ball and add it in one go. Its five numbers travel together, so they can't get out of step the way xs and ys could: one add makes a ball, and one deli removes it, every number included.

for b in all(balls) visits each ball in turn, and b is not a copy of the ball; it is the ball. In Basics 6, s += 10 inside the loop didn't change the scores, because s held a copy of a number. Tables aren't copied like that. b and the item in the list are two names for the same table (like other and ball on slide 1), so b.x += b.dx moves that ball for good.

Drag count. The list starts empty, and each frame _update adds one ball until there are count of them, or removes the newest while there are too many. The slider only changes the count variable, without restarting the program, so _update checks it every frame and catches up. I made it one ball a frame so you can watch them pour in.

Try this

  • Rebuild Basics 6's starfield the object way: a list of star tables, each with its own x, y and speed, so near stars race past and far ones drift (then draw the fast ones brighter). How many adds does each star need now?
  • Drag count down to 0, then back up to 20. Are these the same 20 balls you had before? Predict, then watch closely. Why does it work out that way?
  • Make the first ball in the list white with balls[1].col = 7, as the very first line of _update. Predict whether it works, then run it. What does the error tell you? (How many balls are there on the very first frame?) Make it safe with an if from Basics 5.

3 Building objects

Slide 2 wrote the recipe for a ball inside the add. That's fine while balls are made in one place, but this program makes them in two: five at the start, and one more on each press of O. Two copies of the recipe means every future change (a new field, a different speed) has to be made twice, and sooner or later one copy gets missed.

So we give the recipe a name. make_ball is a function, like _update, but one we call ourselves. The names in its brackets, x and y, are its inputs: calling make_ball(240, 135) means that inside the function x is 240 and y is 135. return hands the new table back to the caller, which is how add(balls, make_ball(240, 135)) gets a ball to add. (Basics 8 covers functions properly.)

x = x on line 6 looks odd. The x on the left is the field's name, and the x on the right is the input's value: "give this table a field called x, holding the x we were given".

Each call to make_ball builds a brand-new table, so the five balls in _init all start in the middle but get their own random speeds and colours, and fan out. Click on the cart and press O (Z on a keyboard) to add more at random spots. 8 + rnd(464) keeps each new ball inside the walls (remember Basics 5's ball that started outside them).

Try this

  • Add one = make_ball(0, 0) and two = make_ball(0, 0) at the end of _init, and print(one == two, 8, 20, 7) at the end of _draw. Both have x 0 and y 0: predict whether Lua calls them equal. Then go back to slide 1 and print other == ball. What do you think == is really asking about two tables?
  • Give make_ball a third input, col, so the caller picks the colour: O makes red balls and X makes blue ones. What happens to the five balls in _init if you forget to give them a colour?
  • Make X remove the oldest ball (Basics 6's deli can do it in one line). Which ball is the oldest: the first in the list or the last?

4 Methods

The code that moves a ball still lives in _update, a long way from make_ball, the code that knows what a ball is. An object can carry its own functions instead.

In Lua a function is a value, like a number or a table, so it can sit in a field. Lines 9 and 10 store two in every ball: update = move_ball and draw = draw_ball. There are no brackets after the names, because we're not calling the functions here, only storing them for later. A function kept in an object like this is a method.

move_ball(self) takes the ball it should move as its input, and calls it self. Any name would work, but self is the one Lua programmers use, and it reads well: "move self along by self's speed".

Line 38, b:update(), has a colon. The colon means "call this object's own update, and pass the object itself in". Lua finds move_ball in b's update field and calls it with b as its input, so self is b. b:update() is shorthand for b.update(b).

The payoff is in _update and _draw. They've shrunk to "everyone, update" and "everyone, draw", and know nothing about how a ball moves or what it looks like; the next slide shows why that matters. (Line 9 can mention move_ball before it's written because make_ball doesn't run until _init, and by then Picotron has read the whole file.)

Try this

  • Change b:update() to b.update(), with a dot. Predict what happens, then run it and read the error carefully. Which name is nil, and why isn't it the ball any more?
  • Add the line add(balls, make_ball(240, 135)) on line 13, between the end of make_ball and move_ball, outside any function. Predict, then run it. What does the error say is missing, and why wasn't it there yet?
  • Give the balls a third method, kick, that sets a new random dx and dy. Store it in make_ball like the other two, and make pressing O call b:kick() on every ball.

5 Different kinds of object

Here's where methods pay off: this list holds two kinds of thing, blue balls and orange boxes. Press O to add a ball and X to add a box.

Each kind has its own making function, make_ball and make_box. Both have an x, y, dx and dy, so they share one move function. Each has its own draw: draw_ball draws a circle, and draw_box a square with a white outline, 5 pixels each way from x and y.

The loops at the bottom never ask "are you a ball or a box?" They call o:draw() on every thing in the list (o is for object), and each thing draws itself its own way, because each carries its own draw.

That matters as a game grows. A third kind of thing needs its making function and its methods, and the loops don't change at all. Enemies, bullets, coins and explosions can all share one list, each knowing how to update and draw itself.

Try this

  • In make_box, remove , draw = draw_box from the end of line 40. Predict what happens the moment the loop reaches a box, then read the error. Compare it with the dot error from slide 4: what's nil this time?
  • Give the boxes a different update too: instead of bouncing, they wrap around the screen edges with %, like Basics 6's stars. Which function do you write, and which word in make_box changes?
  • Add a third kind: a ring (circ) whose size pulses with t(). Put a few in _init, and check that you never had to touch the two loops.

6 Removing objects

In a game, objects come and go all the time: bullets hit, coins get collected, sparks burn out. This fountain makes four sparks every frame, each an object with its own position, speed and life: how many frames it has left.

Every frame each spark moves, falls a little (s.dy += 0.08 is gravity) and loses 1 life. At 0, del(sparks, s) removes it, right there inside the loop. Sparks glow yellow and turn red for their last 20 frames, and the counter in the corner shows how many are alive.

Basics 6's puzzle deleted inside all and missed one of the 20s in {40, 20, 20, 90}: all got confused because the item that slid into place had the same value as the one just deleted. Objects don't have that problem. == on tables asks "is this the same table?", not "are the numbers the same?" (slide 3's one == two), so two sparks are never equal, even if every number matches, and deleting the one we're on inside all is safe.

It also settles Basics 6's snow challenge, where a landed flake had to be removed from two lists at once: one del removes the whole spark, every number of it.

Drag lifetime to set how much life each new spark starts with; the fountain grows taller or shrinks. Sparks already flying keep the life they were born with.

Try this

  • At lifetime 60, with four new sparks every frame, how many sparks should be alive at once? Work it out, then set the slider back to 60 and watch the counter settle. Is it exactly what you predicted? If not, follow one spark through its life, frame by frame.
  • At lifetime 120, lots of sparks fall off the bottom of the screen and carry on "living" where nobody can see them. Remove sparks when they go below the screen, as well as when they burn out, and use the counter to prove it worked. (Basics 5's or helps.)
  • Make the fountain move: give it a position of its own that bounces around the screen like slide 1's ball (as an object, of course), and start each new spark there.

7 Putting it together

In this lesson we added:

  • objects: tables with named fields, read and written with a dot
  • lists of objects, where the loop variable is the object, not a copy
  • a function that builds objects, with inputs and return
  • methods, called with a colon
  • different kinds of object sharing one list and one loop
  • removing an object with del inside all

That's how most games keep track of their world. The starter here adds a ball in the middle on each press of O, and every ball carries its own update and draw. Copy it into a new cart and pick an idea below. Next, Basics 8 looks at functions properly: inputs, outputs, local and splitting a program across files.

Try this

  • Trails: give each ball a list of its own recent positions (trail = {} in make_ball). Every frame, add where the ball is now, remove the oldest once there are 10, and draw the trail as small dots behind the ball. That's a list, inside an object, inside a list.
  • A crowd: make holding O add a ball every frame (Basics 4's btn instead of btnp), but never let there be more than 500. When the 500th is there, remove the oldest each time you add a new one.
  • Fireworks: add a second kind of object, a rocket that flies upwards. When its life runs out it removes itself and adds a burst of sparks where it was. Two kinds in one list (slide 5) that come and go (slide 6).
  • For the brave: make the balls bounce off each other. You'll need a loop inside a loop, so every ball can be checked against every other ball, and a test for whether two balls are touching.
