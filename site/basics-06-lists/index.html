Lists

Keep many things under one name, and loop over them all.

1 A list of numbers

So far every variable has held one thing: one x, one speed, one score. But games are full of many things: a row of enemies, a shower of sparks, a high-score table. Giving each one its own name (score1, score2, score3...) gets out of hand very quickly.

A list fixes that. Line 2 makes one with curly brackets: scores = {30, 120, 75}. That's one name holding three numbers, in order. (Lua calls this a table, and a list is the simplest way to use one.)

To get a number back out, put its position in square brackets: scores[1] is the first one, 30, and scores[2] is 120. Picotron's lists count from 1, so the first item is [1], not [0] as in some other languages. And #scores (say it "length of scores") tells you how many items there are.

Each bar's height comes straight out of the list, so if you change a number on line 2, its bar changes with it.

Try this

  • What does scores[4] give? And scores[0]? Predict, then print them on their own: print(scores[4], 300, 160, 7). Then try joining one onto some text with .., the way lines 14 to 16 do. What's different?
  • Add a fourth score to the list. What else do you have to change before a fourth bar shows up? Count the lines, and keep that number in mind for the next slide.
  • You can change an item as well as read it: scores[2] += 1 works just like it does on any variable. Add an _update that makes the middle bar grow every frame, and start again from 0 once it passes 200. (Basics 3's % can do the "start again" part.)

2 Looping over a list

The list has five scores now, and look: there's only one rectfill drawing them all.

You met counting for loops in Basics 3. Here, for i = 1, #scores do counts i from 1 up to the length of the list, and inside the loop i does two jobs at once. It's the position in the list, so scores[i] is the score for this bar. And it's an ordinary number we can do maths with, so i * 60 spaces the bars across the screen and 7 + i gives each one its own colour.

Because the loop asks #scores how far to count, it doesn't care how long the list is. Add a sixth score to line 2 and a sixth bar appears, without a single new line of drawing code. That's the real power of lists: you write the code for one item, and the loop does it for every item.

Try this

  • Change line 6 to count backwards: for i = #scores, 1, -1 do. Before you run it, predict: will the picture change? Then check. What would you have to change to draw the bars in reverse order, last score on the left?
  • Draw the tallest bar in a different colour. First you need to find it: a variable that remembers the biggest score so far, compared with every score in turn. max(a, b) gives the bigger of two numbers, but try print(max(30, 120, 500), 300, 40, 7) first: why can't one max do the whole list?
  • Join the tops of the bars with line, from each bar's top to the next one's. You'll need scores[i + 1]. Where does the loop have to stop, and what goes wrong if it doesn't?

3 Growing and shrinking

Click on the cart, then press O (Z on a keyboard) a few times: each press adds a new bar of random height. Press X and the first bar disappears, and all the others slide left to fill the gap.

add(scores, n) puts n on the end of the list, so #scores goes up by one. deli(scores, 1) deletes the item at position 1 (the "i" is for index, another word for position). Picotron then moves every later item down one place, so the old scores[2] becomes the new scores[1]. That way a list never has a gap in the middle.

There's a sister function, del(scores, 75), which deletes by value: it finds the first 75 in the list and removes that one. They're easy to mix up, so think "deli: the one at this position" and "del: the one equal to this".

Notice the drawing loop needs nothing special for any of this: it already asks #scores how many bars there are, every frame. Pressing X on an empty list is safe too, since there's nothing to delete. Keep pressing O, though, and after 15 bars they march off the right edge.

Try this

  • Cap the list at 10 bars: when an 11th is added, remove the oldest, so the chart scrolls along like a graph of the most recent scores.
  • deli hands back the item it removed, so gone = deli(scores, 1) catches it. Show the last score you removed on screen. What should your program show before anything has been removed yet?
  • Why does deli bother moving everything along? Make X do scores[1] = nil instead. Predict what #scores will say afterwards, and what the drawing loop will make of the gap, then press X and find out.

4 all()

Here's the chart from slide 2 again, drawn a different way. for s in all(scores) do runs the loop once for every item, in order, and each time round s is the item: 30, then 120, then 75, and so on. No scores[i] needed.

What all doesn't give you is the position. Our bars still need spacing out, so line 6 starts x at 60 and line 10 moves it along after each bar. That's the trade-off. When you only care about the values (adding them up, drawing every star, checking every enemy), all is shorter and there's no counter to get wrong. When you need to know where in the list you are, use the counting loop.

all has one more trick: it's written so that you can del the item you're on in the middle of the loop, and it carries on with the item that slid into its place. Games do that all the time, for example removing every enemy that's been hit. (That works almost every time; the last challenge below finds the one catch.)

Try this

  • Print the total of all the scores, and their average, using all to add them up. (What should the total start at, and where should that line go?)
  • Add s += 10 as the first line inside the loop. Will the bars grow taller every frame? Predict, then check. What does that tell you about s?
  • Inside the loop, del(scores, s) every score under 60 and watch those bars vanish. Now change the list to {40, 20, 20, 90} and try again. Did both 20s go? all is written in Lua, and you can read it in Picotron at /system/lib/api.lua: can you work out why?

5 A starfield

Time to put lists to work: 100 stars, every one of them moving, in a program of barely 20 lines.

Each star needs two numbers, an x and a y, so we keep two lists: xs holds every star's x and ys every star's y. Star number 7 is at xs[7], ys[7]. Both lists start empty ({} is a list with nothing in it yet), and _init fills them with add, 100 times, using rnd to scatter the stars across the screen.

Every frame, _update moves each star left by speed. The % 480 is the wrap-around trick from Basics 3: a star that drifts past the left edge, to -1.5 say, comes back as 478.5, just inside the right edge. Drag the speed slider and all 100 stars change at once, because they share one variable.

Notice how carefully the two lists have to stay in step. Every add to xs needs a matching add to ys, in the same order, or star 7's x would end up paired with some other star's y. With two lists that's manageable. With five (colour, speed, size...) it gets fiddly, and in Basics 7 we'll meet objects, which keep each star's numbers together in one place.

Try this

  • Parallax: give each star its own speed, kept in a third list, so some drift slowly while others race past. Then draw the fast ones bright (colour 7) and the slow ones dim (colour 5). Suddenly the sky has depth.
  • Make holding O run deli(ys, 1), and nothing else. Predict what you'll see, then hold it down. Keep holding: where do the stars end up, and why?
  • A wrapped star comes back at the same height every time, so the pattern repeats on every pass. Give it a new random height when it wraps. With % there's no if to hang that on: how can you tell a star has just wrapped?

6 Over to you

That's lists! Here's a little program to start from: each press of O adds a dot at a random spot, and the two lists remember every one of them.

Copy the code into a new cart in Picotron, then pick an idea below and see if you can make it work. There's no single right answer, and breaking things on the way is part of how everyone learns.

Try this

  • Snow: every frame each flake falls a little, and O adds a burst of 20 new flakes along the top of the screen instead of one dot. Then remove flakes once they've landed, from both lists. (Slide 2's backwards loop helps here. Can you see why counting forwards would go wrong?)
  • Give each dot its own colour, kept in a third list. Picotron's rnd has a trick for this: give it a list instead of a number, as in rnd({8, 9, 10, 11, 12}), and see what comes back.
  • Make X undo the most recent dot. The manual's entry for deli shows a way to do it without working out the position yourself.
