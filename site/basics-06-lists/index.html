1 A list of numbers

So far every variable has held one thing: one x, one speed, one score. Games are full of many things: a row of enemies, a shower of sparks, a high-score table. A name for each (score1, score2, score3...) gets out of hand quickly, because every one of them needs its own line of code. This lesson keeps many things under one name, and ends with 100 stars scrolling across the screen in about 20 lines.

A list does that. Line 2 makes one with curly brackets: scores = {30, 120, 75}, one name holding three numbers in order. (Lua calls this a table; a list is the simplest way to use one.)

To get a number back out, put its position in square brackets: scores[1] is the first one, 30, and scores[2] is 120. Picotron's lists count from 1, so the first item is [1], not [0] as in some other languages. #scores (say it "length of scores") is how many items there are.

This first version still draws each bar by hand, on lines 7 to 9, but each height comes out of the list: change a number on line 2 and its bar changes with it.

Try this

  • What does scores[4] give? And scores[0]? Predict, then print them on their own: print(scores[4], 300, 160, 7). Then try joining one onto some text with .., the way lines 14 to 16 do. What's different?
  • Add a fourth score to the list. What else do you have to change before a fourth bar shows up? Count the lines, and keep that number in mind for the next slide.
  • You can change an item as well as read it: scores[2] += 1 works just like it does on any variable. Add an _update that makes the middle bar grow every frame, and start again from 0 once it passes 200. (Basics 3's % can do the "start again" part.)

2 Looping over a list

The list has five scores now, and one rectfill draws them all.

Basics 3's for loop counted to a number; here for i = 1, #scores do counts i from 1 up to the length of the list. Inside the loop i does two jobs. It's the position in the list, so scores[i] is this bar's score. And it's an ordinary number, so i * 60 spaces the bars across the screen and 7 + i gives each one its own colour.

Because the loop asks #scores how far to count, it doesn't care how long the list is. Add a sixth score to line 2 and a sixth bar appears, with no new drawing code. That's what lists are for: we write the code for one item, and the loop does it for every item.

Try this

  • Change line 6 to count backwards: for i = #scores, 1, -1 do. Before you run it, predict: will the picture change? Then check. What would you have to change to draw the bars in reverse order, last score on the left?
  • Draw the tallest bar in a different colour. First you need to find it: a variable that remembers the biggest score so far, compared with every score in turn. max(a, b) gives the bigger of two numbers, but try print(max(30, 120, 500), 300, 40, 7) first: why can't one max do the whole list?
  • Join the tops of the bars with line, from each bar's top to the next one's. You'll need scores[i + 1]. Where does the loop have to stop, and what goes wrong if it doesn't?

3 Adding and removing

Click on the cart, then press O (Z on a keyboard) a few times: each press adds a bar of random height. Press X and the first bar disappears, and the others slide left to fill the gap.

add(scores, n) puts n on the end of the list, so #scores goes up by one. deli(scores, 1) deletes the item at position 1 (the "i" is for index, another word for position). Picotron then moves every later item down one place, so the old scores[2] becomes the new scores[1], and the list never has a gap in the middle.

Its sister function, del(scores, 75), deletes by value: it finds the first 75 in the list and removes that one. The two are easy to mix up: deli removes the one at this position, del the one equal to this.

The drawing loop needs nothing new for any of this, because it already asks #scores how many bars there are, every frame. X on an empty list is safe too, since there's nothing to delete. Keep pressing O, though, and after 15 bars they march off the right edge.

Try this

  • Cap the list at 10 bars: when an 11th is added, remove the oldest, so the chart scrolls along like a graph of the most recent scores.
  • deli hands back the item it removed, so gone = deli(scores, 1) catches it. Show the last score you removed on screen. What should your program show before anything has been removed yet?
  • Why does deli bother moving everything along? Make X do scores[1] = nil instead. Predict what #scores will say afterwards, and what the drawing loop will make of the gap, then press X and find out.

4 all()

This is slide 2's chart again, drawn a different way. for s in all(scores) do runs the loop once for every item, in order, and each time round s is the item: 30, then 120, then 75, and so on. No scores[i] needed.

What all doesn't give us is the position. The bars still need spacing out, so line 6 starts x at 60 and line 10 moves it along after each bar. That's the trade-off. When only the values matter (adding them up, drawing every star, checking every enemy), all is shorter and there's no counter to get wrong, so I use it whenever I can. When we need to know where in the list we are, the counting loop is the one.

all has one more trick: it's written so we can del the item we're on in the middle of the loop, and it carries on with the item that slid into its place. Games do this all the time, for example removing every enemy that's been hit. It works almost every time; the last challenge below finds the catch.

Try this

  • Print the total of all the scores, and their average, using all to add them up. (What should the total start at, and where should that line go?)
  • Add s += 10 as the first line inside the loop. Will the bars grow taller every frame? Predict, then check. What does that tell you about s?
  • Inside the loop, del(scores, s) every score under 60 and watch those bars vanish. Now change the list to {40, 20, 20, 90} and try again. Did both 20s go? all is written in Lua, and you can read it in Picotron at /system/lib/api.lua: can you work out why?

5 Starfield

Now a real use for lists: 100 stars, every one of them moving, in about 20 lines.

Each star needs two numbers, an x and a y, so we keep two lists: xs holds every star's x and ys every star's y. Star 7 is at xs[7], ys[7]. Both lists start empty ({} is a list with nothing in it yet), and _init fills them with add, 100 times, using rnd to scatter the stars across the screen.

Every frame, _update moves each star left by speed. The % 480 is Basics 3's wrap-around: a star that drifts past the left edge, to -1.5 say, comes back as 478.5, just inside the right edge. Drag speed and all 100 stars change at once, because they share one variable.

The two lists have to stay in step. Every add to xs needs a matching add to ys, in the same order, or star 7's x ends up paired with some other star's y. With two lists that's manageable. With five (colour, speed, size...) it gets fiddly, and Basics 7 fixes it with objects, which keep each star's numbers together in one place.

Try this

  • Parallax: give each star its own speed, kept in a third list, so some drift slowly while others race past. Then draw the fast ones bright (colour 7) and the slow ones dim (colour 5). Suddenly the sky has depth.
  • Make holding O run deli(ys, 1), and nothing else. Predict what you'll see, then hold it down. Keep holding: where do the stars end up, and why?
  • A wrapped star comes back at the same height every time, so the pattern repeats on every pass. Give it a new random height when it wraps. With % there's no if to hang that on: how can you tell a star has just wrapped?

6 Putting it together

In this lesson we added:

  • lists, [i] for reading and changing an item, and # for the length
  • counting loops that work for a list of any length
  • add, deli and del for growing and shrinking a list
  • all(), and deleting from a list in the middle of it
  • two lists kept in step for things that need more than one number

The starter here adds a dot at a random spot on each press of O, and its two lists remember every one. Copy it into a new cart and pick an idea below. Next, Basics 7 replaces those paired lists with objects.

Try this

  • Snow: every frame each flake falls a little, and O adds a burst of 20 new flakes along the top of the screen instead of one dot. Then remove flakes once they've landed, from both lists. (Slide 2's backwards loop helps here. Can you see why counting forwards would go wrong?)
  • Give each dot its own colour, kept in a third list. Picotron's rnd has a trick for this: give it a list instead of a number, as in rnd({8, 9, 10, 11, 12}), and see what comes back.
  • Make X undo the most recent dot. The manual's entry for deli shows a way to do it without working out the position yourself.
