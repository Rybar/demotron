Moving with btn()

Read the buttons every frame and steer a player around the screen.

4function _update()

1 Where we're going

Welcome! In this lesson we'll build something every game needs: a player you can steer. Ours is just a blue circle, but the way it listens to the keyboard is exactly how a spaceship, a hero or a cursor would.

Click on the cart so it can hear your keys, then hold the arrow keys and move the circle around. The code on the left is the whole program, all 14 lines of it. It might look like a lot right now, but by the end of the lesson you'll know what every line does and why.

Try this

  • Before you read on, make a guess: which lines make the circle move, and which single number would you change to make it faster? Check your guess at the end of the lesson.
  • Hold left and right at the same time. Picotron treats the arrow keys like a real joystick, which can't point both ways at once, so it never reports both as held. Which one wins? Does it depend on which you pressed first?

2 btn() asks a question

Picotron can't guess what you want to do, so your game has to ask. The question is btn(b): "is button b being held down right now?"

If the button is up, the answer is false. If it's held, the answer is a number, 255 for a full press. (Gamepad sticks can give smaller numbers when they're only pushed part of the way.) Inside an if, any number counts as "yes": in Lua, everything except false and nil counts as true.

Each button has a number. 0 to 3 are the directions (left, right, up, down), 4 is the O button and 5 is the X button. On a keyboard, O is the Z key (or C) and X is the X key (or V). A gamepad works too.

The program on the left asks about all six buttons, every frame, and prints the answers. Press some keys and watch them change.

Try this

  • Hold right and down together and watch the answers: they drop from 255 to 181. Picotron treats the arrows like a round joystick, so a diagonal counts as about 71% of the way in each direction (255 × 0.71 ≈ 181). Keep that number in mind for slide 5.
  • Because the answer is a number, you can draw with it. Add a bar for each button whose length is the answer: rectfill(320, y, 320 + (btn(b) or 0) / 4, y + 6, 11). (btn(b) or 0 turns false into 0.)
  • Turn the printout into a little on-screen controller: four circles in a plus shape and two more for O and X, each lit up while its button is held.

3 A place to stand

Before anything can move, the game has to remember where it is. We use two variables for that: x for how far across, and y for how far down.

One thing surprises almost everyone: y counts down from the top. The top-left corner is 0, 0, and bigger y means lower on the screen. Picotron's screen is 480 pixels wide and 270 tall, so 240, 135 is right in the middle.

circfill(x, y, 8, 12) then draws a filled circle at that spot, with a radius of 8 pixels, in colour 12 (blue).

Try this

Copy the code into a new cart in Picotron and run it with Ctrl-R:

  • Without trial and error, work out the x and y that put the circle snugly in the bottom-right corner, completely on screen. (The screen's pixels run from 0 to 479 across and 0 to 269 down, and the radius is 8.) Then run it and see if you were right.
  • Draw a face that's positioned entirely from x and y: a big circle, plus two small eyes like circfill(x - 3, y - 2, 1, 0). Change only x and y and the whole face should move together. This "draw relative to a position" idea is how every game sprite works.

4 Moving right

_update is a function Picotron calls 60 times every second, all by itself. That makes it the perfect place to check the buttons.

Each time it runs, we ask btn(1): is right held? If the answer is yes, we add 1 to x. (x += 1 is shorthand for x = x + 1.) The next time _draw runs, the circle appears one pixel further right. Do that 60 times a second and it looks like smooth movement.

Hold right and watch it go. Now try left. Nothing happens, because the program never asks about left. A game only reacts to the questions you write.

Try this

  • Delete cls(1) from _draw and hold right. Why does it leave a trail? What does that tell you about what the screen looks like before each _draw?
  • Give the circle momentum: add a variable vx = 0. While right is held, add a little to vx (say 0.1); every frame, add vx to x. What happens when you let go? How could you make it slow down again?

5 All four ways, and speed

Four questions now, one for each direction. Left and right change x; up and down change y.

There's one more change: instead of moving by 1, each line moves by speed, a variable of its own. If we want a faster player we change one number, instead of hunting through four lines.

Drag the speed slider under the code. See how the highlighted number in the code changes with it? That's the value the running program is using right now.

Try this

  • Remember 181 from slide 2? Use it to fix the fast diagonal. Replace the two left/right lines with the trick from Picotron's manual: x += speed * ((btn(1) or 0) - (btn(0) or 0)) / 255, and do the same for y with buttons 3 and 2. Now compare straight and diagonal movement again. Why does it work?
  • Make the screen wrap around: when the circle leaves one edge, it comes back on the opposite side. (The btnp demo on the next slide does it for one edge.)

6 btn() or btnp()?

Picotron has a second button question: btnp(b). The "p" stands for pressed.

btn is true on every frame the button is held, so the blue circle glides along smoothly. btnp is only true on the frame the press starts, then again every so often if you keep holding, a bit like a key repeating when you hold it down in a text editor. That's why the orange circle hops 16 pixels at a time.

So which do you use? btn for anything that moves continuously, like walking or steering. btnp for things that should happen once per press: menus, moving on a grid, firing a single shot.

Try this

  • Turn the four-way program into grid movement: each press moves the circle exactly 16 pixels, so it always sits in the middle of a 16 × 16 square. Draw the grid lines with line to check it lines up.
  • btnp starts repeating after 30 frames, then every 8. The manual lets you change that: poke(0x5f5c, 12) sets the first delay and poke(0x5f5d, 4) the repeat (both in frames). Put them in _init, try a few values, and decide what would feel right for a menu, and for grid movement.

7 Over to you

That's everything you need to move a player! Here's the four-way program again, with one addition: a col variable for the circle's colour. Nothing changes it yet. That's your job.

Copy the code into a new cart in Picotron, then pick an idea below and see if you can make it work. There's no single right answer, and breaking things on the way is part of how everyone learns.

Try this

  • Turn the circle red (colour 8) while the O button is held, and blue again when you let go. (Think about what col should be on frames when O isn't held.)
  • A dash: tapping X jumps the circle 40 pixels in whichever direction it's currently moving. You'll need to remember the last direction, even on frames when no arrow is held.
  • Add a second circle that you steer with W, A, S and D (buttons 8 to 11: left, right, up, down). Then make both circles change colour while they touch. Two circles touch when the distance between their centres, sqrt(dx * dx + dy * dy), is less than the two radii added together.
