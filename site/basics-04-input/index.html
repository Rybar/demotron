1 The finished program

Every game needs something the player steers. In this lesson we build one: a blue circle that moves with the arrow keys. It's only a circle, but a spaceship, a hero or a cursor reads the keyboard in exactly the same way.

Click on the cart so it can hear your keys, then hold the arrow keys to move the circle around. The code on the left is the whole program, all 14 lines of it. The rest of the lesson builds it up a piece at a time, so by the end every line has a reason.

Try this

  • Before you read on, make a guess: which lines make the circle move, and which single number would you change to make it faster? Check your guess at the end of the lesson.
  • Hold left and right at the same time. Picotron treats the arrow keys like a real joystick, which can't point both ways at once, so it never reports both as held. Which one wins? Does it depend on which you pressed first?

2 Reading the buttons

Picotron can't guess what the player wants, so the game has to ask. The question is btn(b): is button b held down right now?

If the button is up, the answer is false. If it's held, the answer is a number, 255 for a full press. (Gamepad sticks give smaller numbers when they're only pushed part of the way.) Inside an if, any number counts as yes, because in Lua everything except false and nil counts as true.

Each button has a number. 0 to 3 are the directions (left, right, up, down), and 4 and 5 are the two action buttons. Picotron calls those two O and X, names that don't depend on whether you're holding a keyboard or a gamepad. On a keyboard, O is Z (or C) and X is X (or V). These lessons always write the key you press, so when you see Z, the code is asking about button 4.

The demo asks about all six buttons every frame and prints the answers. Press some keys and watch them change.

Try this

  • Hold right and down together and watch the answers: they drop from 255 to 181. Picotron treats the arrows like a round joystick, so a diagonal counts as about 71% of the way in each direction (255 × 0.71 ≈ 181). Keep that number in mind for slide 5.
  • Because the answer is a number, we can draw with it. Add a bar for each button whose length is the answer: rectfill(320, y, 320 + (btn(b) or 0) / 4, y + 6, 11). (btn(b) or 0 turns false into 0.)
  • Turn the printout into a little on-screen controller: four circles in a plus shape and two more for Z and X, each lit up while its button is held.

3 Position

Before anything can move, the game has to remember where it is. Two variables do that: x for how far across, and y for how far down.

y counts down from the top, which catches out nearly everyone used to graphs at school. The top-left corner is 0, 0, and a bigger y means lower on the screen. Picotron's screen is 480 pixels wide and 270 tall, so 240, 135 is the middle.

circfill(x, y, 8, 12) draws a filled circle at that spot, with a radius of 8 pixels, in colour 12 (blue).

Try this

Copy the code into a new cart in Picotron and run it with Ctrl-R:

  • Without trial and error, work out the x and y that put the circle snugly in the bottom-right corner, completely on screen. (The screen's pixels run from 0 to 479 across and 0 to 269 down, and the radius is 8.) Then run it and see if you were right.
  • Draw a face that's positioned entirely from x and y: a big circle, plus two small eyes like circfill(x - 3, y - 2, 1, 0). Change only x and y and the whole face should move together. This "draw relative to a position" idea is how every game sprite works.

4 Moving right

We start with the simplest movement there is: one direction. Picotron calls _update 60 times a second (Basics 2), so that's where we check the buttons.

Each time it runs, we ask btn(1): is right held? If so, we add 1 to x. (x += 1 is shorthand for x = x + 1.) The next _draw paints the circle one pixel further right. Sixty of those a second looks like smooth movement.

Hold right and watch it go. Now try left. Nothing happens, because the program never asks about left. A game only reacts to the questions we write.

Try this

  • Delete cls(1) from _draw and hold right. Why does it leave a trail? What does that tell you about what the screen looks like before each _draw?
  • Give the circle momentum: add a variable vx = 0. While right is held, add a little to vx (say 0.1); every frame, add vx to x. What happens when you let go? How could you make it slow down again?

5 Four directions and speed

Four questions now, one for each direction. Left and right change x; up and down change y.

The other change is that each line moves by speed instead of by 1. When we want a faster player we change one number, instead of hunting down the same number in four separate lines.

Drag the speed slider under the code. The highlighted number in the code follows it: that's the value the running program is using right now.

This version still has a flaw. Hold two arrows at once and the circle moves faster on a diagonal than it does in a straight line. The first challenge below fixes that.

Try this

  • Remember 181 from slide 2? Use it to fix the fast diagonal. Replace the two left/right lines with the trick from Picotron's manual: x += speed * ((btn(1) or 0) - (btn(0) or 0)) / 255, and do the same for y with buttons 3 and 2. Now compare straight and diagonal movement again. Why does it work?
  • Make the screen wrap around: when the circle leaves one edge, it comes back on the opposite side. (The btnp demo on the next slide does it for one edge.)

6 Single presses

Picotron has a second button question: btnp(b). The "p" stands for pressed.

btn is true on every frame the button is held, so the blue circle glides along smoothly. btnp is true only on the frame the press starts, then again every so often while the button stays down, like a key repeating when you hold it in a text editor. That's why the orange circle hops 16 pixels at a time.

I use btn for anything that moves continuously, like walking or steering, and btnp for things that should happen once per press: menus, moving on a grid, firing a single shot. A menu that moved one item for every frame btn says yes would skip fifteen items if you held the key for a quarter of a second.

Try this

  • Turn the four-way program into grid movement: each press moves the circle exactly 16 pixels, so it always sits in the middle of a 16 × 16 square. Draw the grid lines with line to check it lines up.
  • btnp starts repeating after 30 frames, then every 8. The manual lets you change that: poke(0x5f5c, 12) sets the first delay and poke(0x5f5d, 4) the repeat (both in frames). Put them in _init, try a few values, and decide what would feel right for a menu, and for grid movement.

7 Putting it together

In this lesson we learned:

  • btn(b), which answers false, or a number (255 for a full press)
  • the button numbers: 0 to 3 for the arrows, 4 for Z (O) and 5 for X
  • x and y for position, with y counting down from the top
  • a speed variable, so the player's speed lives in one place
  • btnp(b) for things that happen once per press

The starter is the four-way program again, with one addition: a col variable for the circle's colour. Nothing changes it yet; that's the first idea below. Copy the code into a new cart in Picotron. Next, Basics 5 uses if and comparisons to keep the player on the screen.

Try this

  • Turn the circle red (colour 8) while Z is held, and blue again when you let go. (Think about what col should be on frames when Z isn't held.)
  • A dash: tapping X jumps the circle 40 pixels in whichever direction it's currently moving. You'll need to remember the last direction, even on frames when no arrow is held.
  • Add a second circle that you steer with W, A, S and D (buttons 8 to 11: left, right, up, down). Then make both circles change colour while they touch. Two circles touch when the distance between their centres, sqrt(dx * dx + dy * dy), is less than the two radii added together.
